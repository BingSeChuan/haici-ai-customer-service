# 数据库设计

数据库：MySQL 8（Docker 部署，`backend/docker-compose.yml`），字符集 `utf8mb4`。
ORM：SQLAlchemy 2.x。向量数据存于 Chroma（本地文件模式），MySQL 只存业务元数据。

## 表结构说明

### users — 用户

| 字段 | 类型 | 说明 |
|------|------|------|
| id | INT PK AUTO_INCREMENT | |
| phone | VARCHAR(20) UNIQUE | 手机号注册（与邮箱二选一） |
| email | VARCHAR(100) UNIQUE | 邮箱注册 |
| nickname | VARCHAR(50) | 昵称 |
| password_hash | VARCHAR(200) | bcrypt 哈希，不存明文 |
| is_admin | BOOLEAN | 管理后台权限标记（种子数据创建管理员） |
| created_at | DATETIME | |

### sessions — 会话

| 字段 | 类型 | 说明 |
|------|------|------|
| id | INT PK | |
| user_id | INT FK→users | 级联删除 |
| title | VARCHAR(100) | 首问前 20 字 |
| intent | VARCHAR(20) | 会话主要意图（产品咨询/售后问题/闲聊/投诉），加分项标注 |
| created_at / updated_at | DATETIME | updated_at 随消息更新，用于列表排序 |

### messages — 消息

| 字段 | 类型 | 说明 |
|------|------|------|
| id | INT PK | |
| session_id | INT FK→sessions | 级联删除 |
| role | VARCHAR(10) | user / assistant |
| content | TEXT | 消息内容（助手消息为完整回答） |
| intent | VARCHAR(20) | 该问题识别出的意图 |
| sources | JSON | 引用来源数组 `[{doc_name, excerpt, similarity}]`，前端渲染来源卡片 |
| followups | JSON | 追问建议数组 `["..."]`，回答完成后生成并落库（刷新后仍可见） |
| is_fallback | BOOLEAN | 检索为空时的兜底回复标记 |
| created_at | DATETIME | |

**设计要点**：sources 以 JSON 冗余存储而非关联表——来源是回答时刻的快照，且不参与检索/统计，JSON 列读写成本最低；同时保留 doc_name 便于前端直接渲染。

### feedback — 消息反馈

| 字段 | 类型 | 说明 |
|------|------|------|
| id | INT PK | |
| message_id | INT FK→messages | 级联删除 |
| user_id | INT FK→users | 同一用户对同一消息仅一条（重复提交覆盖） |
| feedback_type | VARCHAR(10) | like / dislike |
| text | TEXT | 选填文字反馈（≤500 字） |
| created_at | DATETIME | |

### documents — 知识库文档元数据

| 字段 | 类型 | 说明 |
|------|------|------|
| id | INT PK | 同时作为 Chroma 中向量的 `doc_id` 关联键 |
| user_id | INT FK→users | 文档归属 |
| knowledge_base_id | INT FK→knowledge_bases | 所属知识库（多知识库加分项） |
| name | VARCHAR(255) | 原始文件名 |
| doc_type | VARCHAR(10) | txt / md / pdf |
| status | VARCHAR(20) | processing → ready / failed 状态机 |
| chunk_count | INT | 分块数（就绪后回填） |
| file_path | VARCHAR(500) | 上传文件落盘路径 |
| error_msg | VARCHAR(500) | 失败原因（供前端展示） |
| created_at | DATETIME | |

**向量数据与元数据的关联**：Chroma 中每个分块的 metadata 记录 `doc_id`（= documents.id）、`doc_name`、`knowledge_base_id`（多知识库路由依据）、`category`（规则/FAQ/产品分类）、`chunk_index`。删除文档时按 `doc_id` 过滤清除全部向量（`DELETE /api/knowledge/{id}` 内完成），保证两侧数据一致；检索时可按 `knowledge_base_id` 过滤实现指定库问答。

### knowledge_bases — 知识库（加分项）

用户可创建多个知识库，文档归属知识库。种子数据创建 id=1 的"示例知识库"存放预置文档。

### daily_usage — 每日提问计数（业务规则）

| 字段 | 类型 | 说明 |
|------|------|------|
| id | INT PK | |
| user_id | INT FK→users | |
| usage_date | DATE | 自然日 |
| question_count | INT | 当日已提问数 |

唯一约束 `(user_id, usage_date)`。每次问答前先检查再自增，超过 `DAILY_QUESTION_LIMIT`（默认 100，可配置）返回 429。该表同时为管理后台"近 7 日问答量"折线图提供数据。

## 索引设计

- `sessions.user_id`、`messages.session_id`、`documents.user_id`、`feedback.message_id`、`daily_usage.user_id`：均建普通索引，覆盖列表查询与级联删除
- `users.phone` / `users.email`：唯一索引（登录查找）
- `daily_usage(uq_user_date)`：联合唯一（每日计数幂等）

## 初始化脚本

`backend/scripts/init_db.py`：建表 + 创建管理员（13800000000 / admin123，is_admin=true）+ 创建示例知识库。
`backend/app/main.py` 启动时自动将 `data/seed_docs/` 下的示例文档向量化（幂等：已 ready 跳过）。
